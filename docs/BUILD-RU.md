# Builder для Windows 11 x64

Готовый `PoeAdaptive.Builder.exe` находится в отдельном ZIP выпуска.
Он включает .NET Runtime: сначала собирать Builder и устанавливать Visual Studio
не нужно. Oodle и игровые установки для сборки не нужны.

Выберите корень распакованных исходников (`PoeRedux.slnx`) и отдельный каталог
результата. В окне показаны версия проекта, закреплённый SDK, текущий этап,
журнал, отмена и кнопка открытия готового результата.

Закреплён Microsoft .NET SDK 10.0.403. Если его нет, GUI предлагает установить
его в `%LOCALAPPDATA%/PoeAdaptive/Builder/SDK/10.0.403`. Загружается официальный
ZIP `builds.dotnet.microsoft.com`, SHA-512 сверяется с `build/sdk.json`, после
распаковки проверяется версия. Установка не требует администратора и не меняет
системный PATH. Подтверждение загрузки требуется, потому что она использует
интернет и несколько ГиБ диска. Не устанавливайте SDK из неофициальных зеркал.

## Один процесс для GUI, CLI и CI

Модуль `PoeAdaptive.Build.Core` создаёт снимок исходников, выполняет locked
restore, собирает решение, **запускает консольный PoeAdaptive.Tests**, публикует
Release win-x64 self-contained приложение, диагностику и Builder. Он формирует
два ZIP с EXE, документацией, лицензиями и соответствующим исходным ZIP,
отдельный исходный ZIP, `source-manifest.json`, `build-info.json`, `SHA256SUMS.txt`.

Git-коммит и признак локальных изменений берутся до создания снимка.
Точный идентификатор снимка вычисляется по SHA-256 каждого включённого файла;
архив содержит именно этот снимок, а не более позднее состояние каталога.
Без Git идентификатор снимка сохраняется, Git-поля будут `null`.

Готовый результат появляется только после всех проверок и упаковки в отдельной
папке `PoeAdaptive-0.2.0-<дата>-<идентификатор>`. При ошибке или отмене такой
папки нет. Кнопка «Отмена» завершает дерево дочерних процессов; временные
папки удаляются только внутри собственного `.PoeAdaptive-builder-<guid>`.

```powershell
# Скрипт в исходниках. При отсутствии SDK -InstallSdk разрешает подготовку.
.\Build.ps1 -Source 'C:\Исходники\poe-adaptive' -Output 'D:\Сборки PoE' -InstallSdk
# Подготовленные пакеты и runtime packs берутся из обычного NuGet-кэша.
.\Build.ps1 -Source 'C:\Исходники\poe-adaptive' -Output 'D:\Сборки PoE' -Offline
# Другой управляемый каталог SDK:
.\Build.ps1 -SdkCache 'D:\SDK cache' -InstallSdk
# Готовый Builder без GUI. В PowerShell используйте ожидание процесса для WinExe.
$p = Start-Process .\PoeAdaptive.Builder.exe -ArgumentList '--build --source "C:\Исходники\poe-adaptive" --output "D:\Сборки PoE" --offline' -PassThru -Wait
$p.ExitCode
# То же ядро через уже установленный SDK:
dotnet run --project PoeAdaptive.BuildHost -c Release -- --source . --output artifacts
```

Параметры `Build.ps1`: `-Source`, `-Output`, `-InstallSdk`, `-Offline`, `-SdkCache`.
CLI: `--source`, `--output`, `--install-sdk`, `--offline`, `--sdk-cache`, `--dotnet`.
Коды завершения: 0 — готово, 1 — ошибка, 2 — отменено.
`Build.cmd` вызывает PowerShell-скрипт двойным щелчком и оставляет ошибку на экране.
Из исходного ZIP скрипт сначала запускает BuildHost через SDK; из папки готового
Builder он использует EXE. Бизнес-логика сборки едина; PowerShell выполняет
минимальный bootstrap, необходимый до появления .NET SDK.

## Кэш и ошибки

Первый restore загружает NuGet-зависимости и Windows runtime packs.
Режим `--offline` отключает сетевые источники у restore снимка и использует
подготовленный NuGet-кэш. Для другой версии проекта/SDK могут потребоваться
дополнительные загрузки; Builder сообщает об этом до restore. Для запуска скрипта из исходников также нужен подготовленный NuGet-кэш BuildHost;
его предварительный restore в режиме -Offline использует только локальный источник.
Готовый Builder не требует предварительного restore BuildHost.

Недоступный интернет/неполный кэш, неправильный SDK или SHA-512, отказ доступа,
нехватка места, ошибка restore/компиляции/проверок останавливают сборку.
Для подготовки рекомендуется минимум 5 ГиБ в каталоге результата и около
3 ГиБ для SDK; фактическая потребность зависит от кэша. Пути передаются
процессам отдельными аргументами, включая пробелы и кириллицу.

## CI и выпуск

`ci.yml` использует закреплённый SDK и общую сборку, открывает оба WPF-окна,
проверяет bootstrap SDK в пустом каталоге и повторную headless-сборку готовым
Builder с offline restore и кириллицей в путях. Артефакт включает два пакета,
исходники и контрольные суммы одного коммита.
`release.yml` принимает только успешный Build and test этого репозитория,
проверяет источник, версию и контрольные суммы и публикует через GitHub Actions.
Ручная проверка на Windows 11 и запуск на настоящих играх — отдельные этапы.
