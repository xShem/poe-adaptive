# Архитектура и пределы проверок

## Модель

`GameInstall` разделяет GameId, ClientKind, корень, ResourceFormat,
путь ресурса, свидетельство версии лаунчера и ResourceVersion/BuildId.
SteamInstall оставлен как совместимый формат старого адаптера.
`IInstallationAdapter` отвечает за обнаружение и обновление свидетельств;
`IResourceAdapter` — за подготовку, завершение и проверку ресурсов.
Каталог правил выбирается через GameId; AppId используется только для Steam
и импорта данных 0.1.0. `VersionTracker` различает исходное состояние,
собственную запись, новую подтверждённую версию и неизвестное изменение.

## Проверенные сигнатуры LibGGPK3 2.7.5

Исходник зависимости включён в `third-party/LibGGPK3`, upstream
`f2e1a39b3f99b4c1f35a6dd22754d43cc58d208c`.

- `GGPK(string)` открывает файл ReadWrite.
- `GGPK(Stream, bool leaveOpen=false)` — флаг времени жизни, не режим чтения.
- `BundledGGPK(string, bool parsePathsInIndex=true)` — второй аргумент управляет
  разбором путей, не режимом чтения.
- `BundledGGPK(Stream, bool leaveOpen=false, bool parsePathsInIndex=true)` —
  оба флага не запрещают запись.
- `GGPK.Dispose` вызывает Flush/RenewHashes на доступном для записи потоке.
  Для анализа используется явно FileAccess.Read; поток освобождается отдельно,
  поскольку Dispose библиотеки рано возвращается для read-only потока.
- `Index(Stream, bool leaveOpen=false, bool parsePaths=true, IBundleFactory?)`
  также не имеет флага read-only. Фабрика оригинальных ресурсов читает их
  из Read-only потока; все записи индекса и новых bundles идут в staging.

GGPK не патчится на месте. Полная исходная копия, отдельная подготовленная
копия, повторное открытие, разбор путей/новых bundles и SHA-256 предшествуют
замене целого файла на том же томе. Оригинал сохраняется в каталоге данных.
Копирование, журнал и атомарное переключение имеют отдельные проверяемые этапы.

## Автоматические проверки

Консольный раннер сохраняет 20 исходных проверок и расширен до 40 групп:
VDF, форматы bundle/GGPK, свидетельства GGG/Epic, ручной выбор, ошибочная игра,
несколько установок, версии и собственные патчи, изоляция, legacy state/rules/profiles,
файловые блокировки/место, неизвестный журнал и все четыре контрольные точки
публикации для обоих форматов; SDK hash/pin, ошибки и отмена процессов,
кириллица/пробелы и отбор снимка исходников.

**Синтетический GGPK настоящий по структуре записей, но не содержит настоящих
Oodle-ресурсов игры.** Тесты подтверждают чтение без записи, операции над записями,
публикацию/точное восстановление и обработку сбоя. Они не подтверждают сквозное
декодирование/кодирование ресурсов игры через Oodle и семантику преобразований.
Идентификация GGG в синтетических тестах имеет явно подставленное свидетельство;
реальные ProductName/FileDescription нуждаются в локальной диагностике.

В Windows CI дополнительно собираются все проекты, выполняется раннер,
публикуются self-contained EXE, открываются оба главных окна, загружается и
проверяется SDK в чистом кэше, запускается повторная самостоятельная сборка
готовым Builder с локальным restore. Факт настройки workflow не является
фактом успешного запуска: доказательство — ссылка на успешный run в PR/выпуске.

Windows CI не считается ручной проверкой Windows 11. Настоящих клиентов
в среде разработки нет; ручная проверка Windows 11 и игровых ресурсов не
выполнена. Необходимо проверить Oodle, реальные свидетельства версий,
состояния встроенного лаунчера GGG, активное обновление Epic и фактический
результат функций на текущих игровых сборках.
